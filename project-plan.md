# OCI Vendor Package Scaffolder (OVPS)

## 1. Project Overview

Project Name:
OCI Vendor Package Scaffolder (OVPS)

Purpose:
Design and implement a standardized, machine-enforceable framework that scaffolds, validates, and maintains vendor delivery packages for Docker / OCI-based deployments.

This document is intended to be used directly by automated coding agents (Claude Code, OpenAI Codex) as the authoritative specification for building the project. All assumptions must come from this file.

---

## 2. Design Constraints (Non-Negotiable)

1. Container runtime is Docker / OCI only
2. Offline operation is required (no internet access assumed)
3. All vendors must use an identical structure
4. Automation-first design (everything must be scriptable)
5. POSIX-compliant shell scripts only
6. Docker Compose is the orchestration baseline
7. No Kubernetes support
8. Immutable versioning (no in-place modification of delivered artifacts)

---

## 3. High-Level Goals

- Automatically scaffold vendor delivery packages
- Enforce a strict directory and script contract
- Support install, upgrade, validation, and health checks
- Simplify DevSecOps intake and ATO documentation
- Eliminate vendor-specific handling logic

## 6. File and Directory Contracts

### 6.1 manifest.yaml

The manifest is the single source of truth for the vendor package.

Required fields:
- vendor
- product
- package_version
- container_runtime
- delivery_formats
- compose_required
- persistent_data

The manifest is used for validation, automation, and audit.

---

### 6.2 docs/

Documentation must be plain text only.

Required files:
- overview.txt: system description and architecture
- install.txt: clean install instructions
- upgrade.txt: upgrade paths and assumptions

---

### 6.3 containers/

Rules:
- Only versioned subdirectories (vX.Y.Z)
- One folder per release
- No registry pulls
- Containers must be provided as .tar.gz or .oci files

containers.yaml must enumerate all container images and formats.

---

### 6.4 compose/

Rules:
- docker-compose.yaml must run standalone
- Only local images may be referenced
- docker-compose.override.yaml is optional

---

### 6.5 scripts/

The following scripts MUST exist and MUST have identical intent across all vendors:

validate_environment.sh
- Verifies Docker installation
- Verifies disk space
- Verifies CPU architecture

validate_containers.sh
- Loads container images
- Verifies image metadata
- Fails on load errors

install.sh
- Validates environment
- Validates containers
- Deploys using Docker Compose

upgrade.sh
- Handles version transitions
- Preserves persistent data

healthcheck.sh
- Confirms containers are running
- Confirms exposed services respond

Script rules:
- POSIX shell only
- No internet access
- Idempotent behavior
- Explicit exit codes
- Verbose logging

---

### 6.6 data/

persistent/
- Mounted as volumes
- Persists across restarts
- Empty by default

sample_data/
- Sample or synthetic data
- Used for testing and validation

schemas/
- Database schemas and migrations
- Non-destructive by default

---

### 6.7 checksums/

sha256.txt must contain checksums for all deliverables to support offline integrity validation.

## 7. Project Phases (Execution Plan)

Phase 1: Base Scaffold Generation
- Generate directory hierarchy
- Create placeholder files
- Insert explanatory comments

Phase 2: Manifest Automation
- Define manifest schema
- Generate default manifest
- Implement manifest validation

Phase 3: Universal Script Contract
- Implement all required scripts
- Enforce naming and behavior

Phase 4: Container Handling
- Support .tar.gz and .oci formats
- Offline image loading
- Metadata validation

Phase 5: Data and Persistence
- Volume mapping
- Sample data injection
- Schema loading hooks

Phase 6: Compose Orchestration
- Generate compose templates
- Wire services and volumes

Phase 7: Integrity Verification
- Generate SHA256 checksums
- Validate checksums during install

## 8. Validators

Validators must be machine-executable and enforce:
- Directory completeness
- Script presence and executability
- Manifest correctness
- Docker Compose validity
- Container load success

## 9. Prompting Guidance for Claude Code / Codex

Automated coding agents MUST follow these rules:

- Do not invent structure beyond this document
- Follow directory and file names exactly
- Prefer clarity over cleverness
- Add comments explaining intent
- Fail fast on validation errors
- This document overrides all default assumptions

---

## 10. Acceptance Criteria

A vendor package is compliant if:
- All required directories and files exist
- Scripts run without modification
- Containers load offline
- docker-compose up succeeds
- Persistent data survives restart
- Sample data can be loaded
- Checksums validate successfully
